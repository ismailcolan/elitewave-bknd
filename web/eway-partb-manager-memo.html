E-Way Bill Part-B integration — proposal for management

Sync vehicle and hub movement from Elite Wave to the GST e-way bill portal, with audit trail and vehicle history.

We propose connecting Elite Wave to the government e-way bill system so that when we assign or change a vehicle at a hub, the official e-way bill (Part-B) is updated—not only our internal “truck” field on the GCN.

Executive summary

Consignments already carry e-way bill numbers and expiry dates. Vehicles are often assigned later—or changed across hubs (transshipment). GST expects those movement details on the e-way bill. Today we enter data in Elite Wave but do not push updates to GST automatically. This project adds controlled Part-B updates, logging, and a vehicle history timeline for operations and compliance.

Problem today

  • E-way number is captured on booking; vehicle field is frequently empty until dispatch.
  • Hub-to-hub changes (new truck at Bangalore, Gurgaon, etc.) may not be reflected on the GST portal.
  • Staff may log in to the e-way portal manually—slow, error-prone, hard to audit.
  • Mismatch between ERP vehicle and GST e-way bill creates compliance and checkpoint risk.

What the NIC API document says

India’s e-way bill system (run by NIC — National Informatics Centre) publishes the technical spec for this feature. Official page: Vehicle number update / Part-B (v1.01) (newer versions use the same idea; action name VEHEWB).

In plain terms, that document defines:

  • When: Update movement on an existing e-way bill (new or changed vehicle, transshipment, first truck assignment).
  • Who: The party that generated the e-way or the transporter assigned on the bill.
  • Rules: Bill must be active and not expired; road needs vehicle; rail/air/ship need transport document no. and date.
  • Reason codes: 1 Breakdown, 2 Transshipment, 3 Others, 4 First time.
  • Success: GST returns update time and may refresh validity (validUpto)—we mirror that in ERP.

Elite Wave’s Part-B preview and integration plan follow this NIC specification; live go-live requires company API registration and credentials.

What we will build

  • Part-B action on consignment / trip: user confirms vehicle, hub location, reason → system calls GST (API action VEHEWB).
  • E-Way Bill integration service (backend)—not a single “button → API → done”; includes validation, auth, logging, ERP update.
  • Vehicle history per GR: Consignment → E-Way → timeline (date, location, vehicle, action).
  • Audit log of every attempt (success/failure, user, timestamp) for internal and GST-related review.

Preview (no live GST): Screens and flow using real booking EW360/0206 are available for review before development spend on production API.

Business benefits

  • Align ERP vehicle with the official e-way bill.
  • Reduce manual portal work and data-entry mistakes.
  • Support hub-to-hub logistics with a clear vehicle chain.
  • Stronger audit trail for operations and compliance questions.

Decisions required from management

  1. Integration path: Direct NIC API vs GST Suvidha Provider (GSP)—recommend GSP if faster support and onboarding are priorities.
  2. Account owner: Who registers the company on the e-way API portal and holds production credentials?
  3. Roles: Who in Elite Wave may push Part-B (e.g. admin only vs hub operators)?
  4. Process: Is Part-B push mandatory before dispatch / “in transit” from hub?
  5. Budget: GSP fees (if any), development, UAT, and staff training.

Risks and limitations

  • Cannot go live without approved API access and credentials.
  • Only the e-way generator or assigned transporter may update Part-B (GST rules)—product rules needed.
  • Some GCNs contain multiple e-way numbers in one field; process must define one update per bill.
  • Expired or cancelled e-way bills will be rejected by GST—UI must show clear errors.

Approval requested

Approve proceeding from preview (phase 1) to sandbox integration (phase 2), nominate an owner for e-way API registration, and confirm GSP vs direct NIC preference.
